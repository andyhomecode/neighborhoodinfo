## What this project is

An API, called from a Siri Shortcut with a lat/long, that returns data about the area the user is currently driving through — median home values, demographics, crime rate, voting results, and local history — as a short spoken-readable sentence per category.

`research.md` is the original research log: it documents commercial APIs evaluated and rejected, and the free-data-source options considered per category. This file (CLAUDE.md) is the resolved architecture that supersedes the "open decisions" in research.md — read research.md for *why*, this file for *what to build*.

## Architecture

Python throughout. Data has two freshness tiers:

- **Nationwide batch data** (demographics, home values, crime, elections, historic sites, geographic boundaries) — pre-ingested into PostGIS from free bulk government/nonprofit sources, refreshed by a manually-triggered batch job roughly once a year. The API never calls these sources live.
- **History narrative** (place summary, notable events, notable people) — the one category sourced live, from the Wikipedia/Wikidata GeoSearch API, at request time, cached in Postgres so a given location is only fetched once.

### Docker Compose services

Only the always-on pieces run in containers:

- **`postgis`** — Postgres + PostGIS, persistent volume. The sole datastore. Publishes its port to the host so the (non-containerized) ingestion/loader scripts can connect. Built and running (`docker-compose.yml` at repo root, image `postgis/postgis:16-3.4`, local dev credentials — not yet hardened, fine for now since only `localhost:5432` is exposed).
- **`api`** — FastAPI, built and running (`api/main.py`, `api/Dockerfile`, image builds from repo root context so it can `COPY db/` alongside `api/` — see `docker-compose.yml`). Resolves lat/long → GEOID via `db/queries.py` (`ST_Contains` in SQL, not Shapely/Python), queries Postgres per category, checks the `X-API-Key` header, and calls DeepSeek for the spoken `summary` (see "The `api` service" below — this is a live outbound call, same as the live Wikipedia/Wikidata history lookup, see "History category specifics"). Slim image — psycopg2/GeoAlchemy2, no GDAL, confirmed by using a separate `api/.venv`/`api/requirements.txt` from `ingestion/`'s (which does need geopandas). Currently sync (not async) despite FastAPI's async-first design — see "Open decisions."

Public HTTPS exposure (the "Tunnel" this bullet used to describe as undecided) doesn't live in this compose stack at all — it reuses the existing homelab Caddy reverse proxy instead. See "Public exposure" below.

### Ingestion (not containerized)

A local Python venv, run manually (~yearly) against the `postgis` container's published port — not part of the Docker Compose stack. One script per source (TIGER/Line boundaries, Census ACS, Zillow ZHVI, FBI NIBRS crime, election returns, NRHP). Upserts keyed by GEOID (+ year where applicable), so reruns are idempotent. Kept out of Docker deliberately: it runs rarely, and geopandas/GDAL are heavy native dependencies not worth baking into an image for an occasional local script.

`api` and `ingestion` share DB table definitions via `db/` (SQLAlchemy + GeoAlchemy2 models, see below) so schema isn't duplicated between the venv scripts and the containerized API.

Raw pulled files land in `datasets/` (gitignored, not committed — regenerate by rerunning the scripts). Every source downloads via script except crime (FBI's interactive app has no scriptable download endpoint — manual step, then `parse_nibrs.py` does the actual (scripted) heavy lifting). Current status of each source's download script is tracked in the README's "Data sources & how they're pulled" table.

### Data model (Postgres/PostGIS, all keyed by GEOID)

- `geographies` — tract/county/place boundaries (PostGIS geometry), from TIGER/Line.
- `demographics` — GEOID, year, ACS variables: population, age, income, race/ethnicity, poverty, tenure (owner vs. renter-occupied — rental % derives from this), housing type mix (units in structure: detached/attached/2-unit/.../50+/mobile home), median year built.
- `home_values` — county GEOID, ZHVI (value) and ZORI (rent), **latest available month only** (not a time series — as-built, simpler than the originally-sketched year-month history; extend later if trend data is wanted). Coarser resolution than demographics (county, not tract) — accepted limitation, not a bug to fix. Cost-per-square-foot was considered and dropped: Zillow discontinued their bulk per-sqft dataset (checked their current file catalog directly, not just docs — it's gone), and ACS doesn't publish typical home size at tract/county granularity (only in the American Housing Survey, which is national/major-metro only). No free nationwide source exists for this at our granularity.
- `crime` — county GEOID, year, offense code, incident count. Source: the FBI's raw NIBRS master flat file (incident-level, every reporting agency, one year), manually downloaded (see `ingestion/download_fbi_crime.py` — no scriptable endpoint exists) and then aggregated to county level by `ingestion/parse_nibrs.py`, which streams the multi-GB fixed-width file and counts offenses per county using the record layout FBI publishes alongside it (batch-header segments carry each agency's state + county FIPS; offense segments carry the incident date + UCR/NIBRS offense code). We'd originally settled for state-level-only data (the FBI CDE's small "SRS" bulk file) because the interactive app's download endpoint is protected and the county/agency-level API is undocumented and unreachable — the NIBRS master file sidesteps both problems since it's a plain, if huge, downloadable flat file. NCVS was considered and rejected as an alternative: it's national-only, no sub-national geography in the public-use files at all. Scope note: only Group "A" incident-based offenses (segment "02") are counted; Group "B" arrest-only minor offenses (DUI, disorderly conduct, etc., segment "07") are not — see the parser's docstring. No per-city Socrata integrations either — those don't fit a nationwide-batch model and were flagged in research.md as high-maintenance.
- `elections` — county GEOID, year, two-party vote totals (GOP/Dem). v1 scope is the 2024 presidential race only, narrower than the original "federal races" plan — chosen because getting election data automated at all was more valuable than completeness. Source: not MEDSL directly — MEDSL's own Harvard Dataverse blocks all scripted access (AWS WAF bot-challenge, confirmed across the search API, contents API, dataset page, and direct file-access API), so `download_elections.py` instead pulls from [tonmcg/US_County_Level_Election_Results_08-24](https://github.com/tonmcg/US_County_Level_Election_Results_08-24), a well-established, actively-maintained, MIT-licensed community mirror derived from the same official state/AP results — a plain scriptable GitHub raw-file download, no manual step needed. Trade-off versus raw MEDSL: two-party totals only, no third-party candidates. Alaska is reported by state house district and DC by ward, not standard county FIPS — present in the data but not joinable the same way as everywhere else. Senate/House and older cycles are a later addition (MEDSL Dataverse if a scriptable path turns up, or another community mirror). Local (mayor/city council) elections remain out of scope — no standard nationwide source exists.
- `historic_sites` — id, name, site_type (building/object/site/structure/district), city, county_name, state, listed_date, geometry (point or polygon — NRHP points and district polygons share one table, queried by proximity via `ST_DWithin`, not by GEOID). Powers `/history/sites`.
- `zip_centroids` — zip_code, lat, lon, from the Census Gazetteer ZCTA file. Not part of the original data-model plan; added to resolve a ZIP code (e.g. a fixed "home" location) to a lat/long so it can go through the same `resolve_location` path as any other coordinate. Centroid only, not real ZCTA boundary geometry.
- `local_crime_supplement` — county_geoid, year, offense_category, law_category, incident_count, borough_name, source. Not part of the original data-model plan either; a scoped one-off exception for NYC (see "Database & query library" for why and its history — was ZIP+radius keyed originally, now county-keyed), not a general per-city table. PK is `(county_geoid, year, offense_category, law_category)` — the same offense_category can legitimately appear at two law_category severities (e.g. NYPD reports "DANGEROUS DRUGS" as both a felony and a misdemeanor), which collided and crashed the loader once before `law_category` was added to the key.
- `history_cache` — built (`db/models.py`'s `HistoryCache`). Holds `location_key` (lat/lon rounded to 3 decimals, ~111m), lat, lon, `fetched_at`, and `places` (JSON — the classified Wikipedia GeoSearch results for that location). Written by `api/wikipedia.py` at request time, not by ingestion — deliberately excluded from `db/load.py`'s yearly drop-and-reload cycle (see that file's `BATCH_TABLES` list) so a batch refresh doesn't wipe live-fetched history data.

`db/models.py` is the literal, current schema (SQLAlchemy + GeoAlchemy2) — treat it as canonical over this prose if they ever disagree.

### Database & query library (`db/`)

Built and tested. `docker-compose up -d` starts `postgis`; `ingestion/.venv/bin/python -m db.load` (run from repo root) drops/recreates all tables and reloads everything from `datasets/` — a few minutes, ~121k geography rows, 85k demographics, 92k historic sites, etc. Full reload every run, no incremental upsert logic (matches the "batch refresh yearly" model — simpler than it sounds since nothing needs merging).

`db/queries.py` is the function library the `api` service will call directly — no ORM objects leak out, every function returns plain dicts/lists/`None` so a FastAPI route handler can hand results straight to a Pydantic response model:

- `resolve_location(lat, lon)` — tract/county/place GEOIDs + names, or `None` if the point isn't in any tract (ocean, outside the US).
- `resolve_zip(zip_code)` — `(lat, lon)` via the ZIP's ZCTA centroid (`zip_centroids` table, from the Census Gazetteer file — see `ingestion/download_zcta.py`), or `None` for an unknown ZIP. A centroid, not real ZCTA boundary geometry — fine for "approximately where this ZIP is," not for "which ZIP is this exact point in."
- `get_demographics(tract_geoid)`, `get_home_values(county_geoid)`, `get_crime(county_geoid)`, `get_crime_rate(county_geoid, year)`, `get_elections(county_geoid)`, `get_historic_sites(lat, lon, radius_m=5000, limit=5)` — one function per category, each independently callable (matches the per-category endpoint design below). `get_crime_rate` computes incidents per 100k for the county vs. its state vs. nationally, with state/national denominators restricted to counties that actually have NIBRS data for that year — otherwise non-reporting counties' population would dilute the comparison rates and make every real county look artificially low-crime by comparison.
- `get_neighborhood_summary(lat, lon)` — calls all of the above, returns one combined dict. This is what `test_lookup.py` and the eventual `/neighborhood` endpoint both use.
- `compare_to_home(lat, lon, home_zip="10002")` — full `get_neighborhood_summary` for both the target and a fixed home ZIP, plus a `comparison` dict of `{target, home, diff_pct}` for income, rent, home value, renter %, median age, and crime rate, a `same_winning_party_2024` flag, a `political_lean` dict (see below), a `home_local_crime` field, and a `crime_by_category` dict (see below). `diff_pct` is positive when the target is higher than home.
- **`political_lean`**: `{target_gop_pct, home_gop_pct, diff_points, direction}` — a percentage-**point** difference in two-party GOP vote share (`get_elections`'s new `gop_two_party_pct` field: `votes_gop / (votes_gop + votes_dem) * 100`), not the `comparison` dict's relative `_pct_diff`. Relative % would be nonsensical here ("GOP share is 20% higher" doesn't mean anything useful) — the meaningful statement is "target is 15 points more Republican than home," which needs a shared 0-100 scale and a plain subtraction, not a ratio.
- **`get_crime_by_category(county_geoid, year)` / `get_local_crime_by_category(county_geoid, year)`**, merged into `compare_to_home`'s `crime_by_category`: per-category (assault, drug, larceny_theft, burglary, motor_vehicle_theft, robbery, sex_offenses, homicide, weapons, vandalism, fraud, arson, kidnapping, other) rate-per-100k, each with `vs_state_pct`/`vs_national_pct` (same reliability rules as `get_crime_rate`) and `vs_home_pct`. Two offense taxonomies had to be mapped to one shared category list to make this possible at all — `NIBRS_CATEGORY` (3-char NIBRS codes) and `NYPD_CATEGORY` (NYPD's free-text `ofns_desc`), both built directly against the actual distinct values in each table, not a generic reference list. `home_source` on each category (`"local_supplement"` | `"nibrs"` | `None`) records which taxonomy home's number came from — prefers the local NYPD supplement when home's county has one, falls back to home's own NIBRS category rate otherwise, so this works for any home ZIP, not just NYC ones.

  **`MIN_CATEGORY_INCIDENTS = 10`, confirmed necessary, not precautionary.** Before this guard, comparing against home produced `vs_home_pct` values like `+16,250%` and `+36,000%` — traced to home's own category counts being tiny in the NYPD supplement (kidnapping: 1 incident for all of Manhattan in the pulled data; weapons: 3; arson: 3; robbery: 6). `MIN_RELIABLE_INCIDENTS` (the total-crime floor) doesn't catch this — a jurisdiction can clear 100+ incidents in aggregate while still having a near-zero count in one specific category. Below the floor, `home_rate_per_100k`/`home_source`/`vs_home_pct` are all `None` for that category rather than a number. Residual finding even above the floor: several categories that DO clear it still show very large `vs_home_pct` (e.g. assault: +9,772% with 97 home incidents) — this is the underlying NYPD-complaints-vs-NIBRS-offense-records counting-unit gap being genuinely large in magnitude, not a bug to chase further; flagged here rather than silently presented as precise.
- `get_local_crime(county_geoid, year)`, `get_local_crime_rate(county_geoid, year)` — the NYC/NYPD one-off supplement, see below. `None` unless that county has actually been loaded via `ingestion/download_nypd_crime.py`.

**Real finding from building `compare_to_home`, not a hypothetical edge case**: comparing against home ZIP 10002 (NYC) immediately surfaced that NYC's crime data is unusable. All 5 NYC boroughs combined show **2** total incidents in the 2025 NIBRS master file (Manhattan itself: 2; the other four: 0) — versus 367,335 for LA County, 352,935 for Harris County (Houston), and 311,894 for Cook County (Chicago), counties of comparable or smaller population. This isn't a parsing bug (verified directly against the `crime` table) — NYPD is a well-known NIBRS holdout; they track crime thoroughly internally but haven't meaningfully transitioned to submitting it to the FBI's national system. Naively computing "crime rate vs. home" against that near-zero number produced a comparison like *"2,458,400% higher than home"* — confidently wrong, exactly the kind of thing a deterministic (non-LLM) summary generator must never emit.

Fix, in `db/queries.py`: `MIN_RELIABLE_INCIDENTS = 100` — a county's crime data is only trusted (`reliable: True` in `get_crime_rate`'s output) above that floor. Below it: `get_crime_rate` still reports the county's own (meaningless) rate for transparency, but excludes that county from state/national comparison pools entirely (not just flags it — otherwise a state with one big non-reporting city, like NY with NYC, gets its "state average" quietly built almost entirely from smaller reporting counties while looking like it covers the state), and `compare_to_home` suppresses the crime-rate comparison outright (`comparison["crime_rate_per_100k"]["unreliable"] = True`, both values `None`) rather than showing a number. This is a heuristic, not a precise test — a hard incident-count floor will occasionally exclude a genuinely low-crime rural county along with the actually-broken ones. Worth a better test later (e.g. cross-checking against the `ucr_participation` style data BJS publishes) if crime-rate accuracy becomes more important than it is today.

**`local_crime_supplement` — a scoped, one-off exception to "no per-city sources," not a general capability.** Since NIBRS is unusable for NYC specifically, and NYC happens to publish real complaint-level crime data for free with no auth (`ingestion/download_nypd_crime.py`, NYC Open Data's Socrata API, the same data CompStat is built from), pulled 226 real 2025 complaints within 1,500m of ZIP 10002's centroid across 25 offense categories. Deliberately NOT wired into `get_crime_rate`'s comparison machinery — `get_local_crime`/`get_local_crime_rate` are separate functions, and `compare_to_home` surfaces the result as an unlabeled-diff `home_local_crime` field rather than a `{target, home, diff_pct}` entry, because it genuinely isn't the same methodology (NYPD "complaints" vs. NIBRS "offense records" aren't the same counting unit, and it's radius-based, not county-based).

**Revised from ZIP+radius to whole-county.** The original version pulled NYPD complaints within 1,500m of the ZIP 10002 centroid and estimated population by summing every tract that merely intersected that circle — confirmed as a real overcount (45 tracts pulled in, their areas summing to well over the actual ~7.07 km² circle, including one 0-population Brooklyn tract across the East River that just barely clipped the edge). Fixed by switching to whole boroughs instead: NYC's 5 boroughs map 1:1 to counties (Manhattan = New York County = FIPS 36061), so `ingestion/download_nypd_crime.py` now filters NYPD's own `boro_nm` field instead of a radius, `local_crime_supplement` is keyed by `county_geoid` instead of ZIP, and `get_local_crime_rate` uses the real Census county population (`SUM(total_population) WHERE LEFT(geoid,5) = county_geoid`, the same technique `get_crime_rate` uses) — no estimate needed at all anymore. Manhattan, 2025: 1,731 complaints / 1,627,788 people = 106.3 per 100k (close to the old radius estimate of 110, but now exact rather than a confirmed-inflated approximation).

**Performance: a spatial index that existed but was never used.** `get_local_crime_rate`'s population query (and `get_historic_sites`) both call `ST_DWithin(geometry::geography, ...)`, but `db/load.py` had only ever built a GIST index on the plain `geometry` column. Postgres cannot use a plain-geometry GIST index for a query that casts to `::geography` — confirmed via `EXPLAIN ANALYZE`: it was doing a parallel sequential scan filtering `ST_DWithin` against all 85,529 tracts nationwide for every single call. Fix: added `CREATE INDEX ... USING GIST ((geometry::geography))` — an expression index matching the actual cast used in queries — for both `geographies` and `historic_sites` in `db/load.py`. Measured effect: the population query went from 8,831ms to 8.8ms (EXPLAIN ANALYZE, confirmed via query plan change from sequential scan to index scan), `get_historic_sites` from 0.68s to 0.026s, and `compare_to_home` end-to-end from 10.4s to 0.16s. The plain-geometry index is still kept alongside it — `resolve_location`'s `ST_Contains` calls query in raw degrees/SRID 4326 without a cast, and use that one instead. General lesson worth remembering for any future radius/distance query: a GIST index only helps if it's built on the same expression the query actually filters on.

**Tested against three real coordinates** (`test_lookup.py <lat> <lon>`) — chosen as an unplanned real-world validation, not synthetic test data, and the results line up with what's actually true about these places: (41.293, -82.223) resolves to Oberlin, OH and independently comes back with median age 21.4, 27% renter-occupied, *and* the nearest historic site is Oberlin College itself at 248m — three unrelated data sources (ACS, TIGER boundaries, NRHP) agreeing with each other and with reality. (41.203, -79.921), rural Venango County PA, comes back with the lowest income/home-values of the three and drug offenses as the top crime category — consistent with the region's real economic and opioid-crisis profile. Full raw JSON output for all three coordinates is in the conversation history that produced this file; re-run `test_lookup.py` any time to regenerate it.

**Design principle for the `api` layer, stated explicitly because it drove `db/queries.py`'s shape**: the `summary` sentence in every API response must be built **deterministically from these structured fields — template/string-formatting logic, not an LLM call**. `db/queries.py` therefore returns fully-formed, ready-to-template data (e.g. `get_elections` already computes `winner` and `margin_pct`; `get_demographics` already computes `renter_pct`) specifically so the future summary-sentence code can be plain string formatting, not further data munging.

**`OFFENSE_LABELS` gap closed.** Was missing labels for 21 of the 52 distinct offense codes actually present in the ingested crime table (confirmed by diffing `OFFENSE_LABELS`'s keys against `SELECT DISTINCT offense_code FROM crime` on the loaded 2025 file, not a theoretical code list) — codes like `26F` (identity theft, 186k incidents), `370` (pornography/obscene material, 52k), `100` (kidnapping/abduction, 49k) were falling back to showing the raw code. Filled in against the official FBI NIBRS Group A offense-code table; `370` was also added to `NIBRS_CATEGORY` (bucketed under `sex_offenses`, alongside `36A`/`36B`) since it was falling through to `"other"`. Re-verified: zero missing codes in either dict against the live table.

### API surface

Category is a path segment, not a query parameter, so each Siri Shortcut can call one fixed URL. **Implemented** (`api/main.py`):

- `GET /neighborhood?lat=&lon=` — full summary across all categories.
- `GET /neighborhood/housing?lat=&lon=` — demographics + home values.
- `GET /neighborhood/demographics?lat=&lon=`
- `GET /neighborhood/crime?lat=&lon=` — raw offense breakdown + `get_crime_rate`'s state/national comparison.
- `GET /neighborhood/elections?lat=&lon=`
- `GET /neighborhood/history/sites?lat=&lon=` — NRHP only (batch-ingested data; doesn't need the live Wikipedia call).
- `GET /neighborhood/compare?lat=&lon=&home_zip=10002` — `compare_to_home`'s full output (comparison stats + `crime_by_category` + `political_lean`). Not in the original design sketch, added because comparison-to-home became a first-class feature during `db/queries.py` development.
- `GET /neighborhood/history?lat=&lon=` — all nearby Wikipedia-documented places/topics, tagged `category` (person/event/site/other), distance-ordered.
- `GET /neighborhood/history/events?lat=&lon=` — `/history` filtered to `category == "event"`.
- `GET /neighborhood/history/people?lat=&lon=` — `/history` filtered to `category == "person"`.

These three are powered by `api/wikipedia.py` (see "History category specifics" below) — the one live, non-`db/queries.py` data path in the API. Note `/neighborhood` and `get_neighborhood_summary` deliberately do **not** include history — `db/queries.py` stays free of live calls by design, so history stays opt-in per-category.

**`/neighborhood` also takes an optional `utterance` param** — free text like `"tell me about crime here"`, `"housing"`, or `"compare to home"` — for a Siri Shortcut that passes dictated speech straight through instead of hardcoding one category's URL. When present, `api/llm.py`'s `classify_intent(utterance)` makes a `temperature=0`, JSON-mode DeepSeek call to pick one or more of `VALID_CATEGORIES` (`demographics`/`housing`/`crime`/`elections`/`history`/`compare`/`"everything"`), `api/main.py`'s `CATEGORY_BUILDERS` fetches only the data for those categories (kept 1:1 with each single-category endpoint's own data shape), and the response includes a `requested_categories` field so the caller can see what was inferred. A vague/unparseable/multi-category utterance falls back to `"everything"` rather than guessing narrowly or returning nothing — fails open, not closed. `commentary=false` still short-circuits to skip the DeepSeek narration call, but `classify_intent` still runs (it's a separate, cheap call) since the category selection is needed either way. Omitting `utterance` entirely leaves `/neighborhood`'s original full-summary behavior untouched — verified byte-for-byte same response shape as before (no `requested_categories` key) when the param isn't passed.

**`"everything"` gets a longer response, not the same length as a single category.** `generate_commentary(data, long=True)` swaps in `LONG_ADDENDUM` (appended to `SYSTEM_PROMPT`) instructing the model to cover every category in some depth rather than picking one highlight, and raises `max_tokens` from 300 to 900. Measured on Oberlin OH: a single-category ask (`"housing"`) produced ~450 characters of narration; `"everything"` produced ~2,580 — roughly 5-6x longer, confirmed live, not just a token-limit bump that goes unused.

`home_zip` (default `10002`) is accepted alongside `utterance` for when it implies a home comparison (`"compare"`/`"everything"`) — same param `/neighborhood/compare` already uses. **Known limitation, not built**: an utterance like `"compare to LA"` does not resolve "LA" to a ZIP code — `home_zip` only changes if the caller passes it explicitly as a separate query param; the utterance's own wording about *which* home to compare against is not parsed. `"compare to nyc"` only reads correctly today because `10002` (NYC) already happens to be the hardcoded default.

**`"help"` is an eighth, meta category** — not a data category, not in `CATEGORY_BUILDERS`, and deliberately handled before location resolution in `api/main.py`'s route: `if "help" in categories: return ...` short-circuits ahead of `_location_or_404`, so a help request works even at a coordinate the app can't resolve (tested at `lat=0&lon=0`, still `200`), and skips both the DB and the DeepSeek commentary call entirely. The response text itself is **not** LLM-generated — `api/llm.py`'s `help_text()` is a deterministic string built from `CATEGORY_INFO`, the same dict `classify_intent`'s prompt is built from (`_build_intent_prompt()`), so the help text can never describe a category the classifier doesn't actually support — one source of truth, not two hand-maintained lists that could drift apart. Measured: a `"help"` request completes in ~1.2s (just the classification call), versus ~3s+ for anything that also generates commentary.

Every response has the same shape: `{"summary": "...", "data": {...}}` — `summary` is DeepSeek-generated spoken commentary (see "The `api` service" below), `data` is `db/queries.py`'s raw structured output, unchanged. Every endpoint takes `commentary: bool = True` to skip the LLM call (faster/free, useful for testing or a client that wants to build its own sentence). Every request requires the `X-API-Key` header, checked against the `API_KEY` env var — confirmed with real requests: missing/wrong key → 401, right key → 200.

### The `api` service

- **Config**: reads `.env` at repo root (not `ingestion/.env` — a separate file) for `DATABASE_URL` (only used for local/non-Docker runs; the containerized `api` service gets it from `docker-compose.yml`'s `environment:` instead, pointed at the `postgis` service name), `API_KEY` (this API's own auth, a generated random token), and `DEEPSEEK_API_KEY`.
- **`api/llm.py`**: calls DeepSeek's OpenAI-compatible API (`base_url="https://api.deepseek.com"`, model `deepseek-chat`, via the `openai` Python package) with `db/queries.py`'s full structured output as the user message. System prompt explicitly forbids inventing facts not in the JSON and forbids doing its own arithmetic (use the JSON's precomputed `renter_pct`/`margin_pct`/`vs_state_pct`/etc., don't recompute from raw counts) — the model's job is narration, not calculation. ~4 seconds latency per call, tested for real (not mocked) against multiple endpoints and coordinates; e.g. for Oberlin vs. home ZIP 10002 it produced (verified accurate against the underlying data): *"You're in Oberlin, Ohio, and this place is a real outlier. It's a college town with a median age of just 21, which is strikingly younger than your home in New York City, where the median age is about 55..."* — independently surfaced the same "college town" pattern this file's own docs called out from the raw JSON, without being told to look for it.
- **This is a deliberate reversal of the original "deterministic, template-based summary" principle** (see git/conversation history — that was the explicit design goal while `db/queries.py` was being built). The user later got a cheap DeepSeek key and asked for LLM-generated commentary instead, specifically because a human narrating the raw JSON (in conversation, e.g. the Oberlin college-town/Venango opioid-crisis observations) was more interesting than a template ever would be. `db/queries.py`'s design — every function returns fully-computed, ready-to-narrate fields rather than raw counts the caller has to derive stats from — turned out to matter for a different reason than originally intended: it keeps the LLM from doing its own (potentially wrong) arithmetic, not from needing a template engine that no longer exists.
- **Auth**: `require_api_key` FastAPI dependency, checks `X-API-Key` header against `os.environ["API_KEY"]`. Simple shared-secret, no per-client keys or rate limiting — fine for a single-user hobby project behind a tunnel, revisit if that ever changes.
- **Error handling**: `resolve_location`/`compare_to_home` returning `None` → `404`; anything else unhandled → generic `500` (a blanket exception handler, deliberately not leaking internals in the response).

### History category specifics

The only category not fully covered by nationwide batch ingestion — two sources, combined:

- **NRHP** bulk data → batch-ingested like everything else, powers `/history/sites`.
- **Wikipedia/Wikidata GeoSearch** → live call at request time (the one exception to "no live calls"), built in `api/wikipedia.py`, powers `/history`, `/history/events`, and `/history/people`. Results are cached in `history_cache` after first fetch per location (see "Data model" above for why that table survives `db/load.py`'s batch reload).

**Two Wikipedia calls, not one, because distance and enrichment come from different API shapes** — tested live against Oberlin OH and Gettysburg PA, both work as described:

- `list=geosearch` (not `generator=geosearch`) — the *only* form that returns `dist` (meters) per result, already distance-sorted. `generator=geosearch` was the original plan (per this section's earlier draft) but its page objects don't carry distance at all — confirmed directly, not assumed. `gsradius` is capped at 10,000m (10km) by Wikipedia; no way to search wider in one call.
- A second batched call, `prop=extracts|pageterms|pageprops&ppprop=wikibase_item`, on all the pageids from the first call at once (`pageids=1|2|3|...`) — gets `pageterms.description` (the short spoken-summary phrase, e.g. *"private liberal arts college in Oberlin, Ohio, United States"* — prefer this over `extract`, which is intro text truncated at a char limit and cuts off mid-sentence) and `pageprops.wikibase_item` (the Wikidata `Q`-id) for every result in one round-trip, not N drill-down calls.
- **Coverage is real in towns, empty in remote stretches** (as originally expected) — Oberlin OH returned 20 results within 1.4km (the college, Tappan Square, several historic churches/houses, a hospital, a former train station); this is a real characteristic of the data on long empty highway stretches, not a bug to fix.

**Classification (person/event/site/other) — built, but currently degraded by an external outage, not a bug in this code.** `_classify()` in `api/wikipedia.py` uses a single batched Wikidata SPARQL query (`query.wikidata.org/sparql`, one `VALUES` clause with every `Q`-id from the geosearch batch) for `wdt:P31` ("instance of"): `Q5` (human) reliably means "person" — an exact ID match, not a label guess; event/site fall back to a regex over the instance-of *labels* (`EVENT_LABEL_RE`/`SITE_LABEL_RE`, e.g. "battle", "building", "college") — this is the "noisier, cheaper fallback" the original research called out, just applied to Wikidata's structured (if messy) instance-of labels instead of Wikipedia's free-text categories, since P31 is already being fetched to catch `Q5`.

**Found live, not hypothetical**: testing against Gettysburg PA (39.8147, -77.2297) — a location that should surface an obvious event ("Battle of Gettysburg") — the SPARQL call failed with `HTTP 429: Aggressively rate-limiting to 1 req/min - this rule was created during active wdqs outage`. `_fetch_instance_of()` already wraps the call in `try/except (URLError, TimeoutError, JSONDecodeError)` and returns `{}` on failure — by design, since classification is enrichment on top of the core lookup, not something that should break the whole feature if it fails. Confirmed via docker logs that this degrades gracefully: every result still comes back with title/description/extract/distance, just tagged `category: "other"` instead of the correct classification while the outage lasts. **Not yet fixed**: a category-based fallback that avoids WDQS entirely was found and partially verified (Wikipedia's own edit-maintained categories are highly reliable for this — pages about people are tagged e.g. `Category:1829 births`/`Category:1897 deaths`; "Battle of Gettysburg" carries `Category:Battles of the American Civil War in Pennsylvania`) but not wired in — `categories` can be added to the same batched `prop=` call above (`prop=extracts|pageterms|pageprops|categories`) with no extra round-trip, replacing the SPARQL dependency's regex-on-labels approach with a regex-on-category-titles approach that only depends on `en.wikipedia.org`, not a second, less reliable service. Worth doing if WDQS's instability recurs.

### Public exposure

Reachable at `https://server.maxwell.nyc/neighborhoodapi/...` — reuses the existing homelab Caddy reverse proxy (`~/code/infra/caddy/`, container `edge-caddy`) rather than adding a dedicated tunnel/`cloudflared` service to this repo's own compose stack, resolving the "Cloudflare Tunnel/ngrok" open decision from earlier in this file. Cloudflare (DNS + proxy, SSL) → Caddy (path-based routing, TLS termination with Cloudflare Origin certs) → this API on `localhost:8000` (Caddy reaches it via `host.docker.internal:8000`, the same pattern used for Jellyfin/Immich — no shared Docker network needed since the `api` service already publishes its port to the host).

Caddy config: a `@neighborhoodapi_path` matcher + `handle` block in `server.maxwell.nyc`'s existing `Caddyfile` block (alongside the other path-prefixed services already there — Workday MCP, figlet-mcp, Ollama, pelletbro, Minecraft), `uri strip_prefix /neighborhoodapi` then `reverse_proxy host.docker.internal:8000`. No Caddy-level auth layer added (unlike the MCP routes, which gate on a header before proxying) — this API already enforces its own `X-API-Key` check (`require_api_key` in `api/main.py`), so a second gate at the proxy would be redundant. Confirmed via real HTTPS requests through the full chain: correct key → 200 with real data, missing/wrong key → 401 (app-level, not Caddy), a path outside the prefix → 404, and existing routes on the same Caddy instance (Jellyfin, photos, Ollama) unaffected.

**Real gotcha hit and fixed while wiring this up**: editing `Caddyfile` on the host and running `caddy reload` inside the `edge-caddy` container was not enough — a text-editing tool that writes via replace-then-rename (atomic write, not in-place edit) changes the file's inode, and Docker's single-file bind mount is pinned to the original inode, not the path. The container kept serving the pre-edit config (confirmed: `docker exec edge-caddy wc -l /etc/caddy/Caddyfile` showed the old line count even after a successful `caddy reload`), so the new route 404'd with an empty body — Caddy's own catch-all responding, not the proxied app returning anything. Fix: `docker compose restart caddy` (full container restart, not just a config reload) after any host-side edit to `Caddyfile`. Documented in `~/confignotes/thinkcentre-reference.md` since it'll bite again on the next Caddy edit, not specific to this project.

**Also found while testing this**: `.env`'s `API_KEY` had been rotated (old value commented out, new value `CedarPointBonineFury325` set) sometime after the API container was last started — the running container still had the old key baked into its environment (`env_file` is only read at container creation, not on every request), so requests with the new key from `.env` 401'd until `docker compose up -d api` recreated the container. Worth remembering any time `.env` changes: the container needs to be recreated, not just left running, for the new values to take effect.

## Open decisions for v1

- History person/event/site classification currently degrades to `"other"` for everyone during Wikidata Query Service outages (confirmed live against Gettysburg PA — see "History category specifics"). A category-based fallback that avoids WDQS entirely was identified and partially tested but not wired in; worth doing since WDQS's rate-limiting/outage behavior was observed directly, not assumed to be reliable.
- Cache invalidation/refresh policy for `history_cache` — built, but with no expiry: a cached location is never refetched, so a location whose classification landed as `"other"` during the WDQS outage above will stay that way until the cache row is manually cleared or a TTL gets built.
- How to avoid overlap between NRHP `sites` (from `historic_sites`/`/history/sites`) and Wikipedia/Wikidata `events`/`people`/`site`-classified results (from `/history`) for the same physical location — e.g. Oberlin College shows up as a Wikidata "site"-classified result and would also plausibly appear in `/history/sites`'s NRHP radius search. Not deduplicated between the two data sources.
- `api`'s route handlers are sync `def`, not `async def` — FastAPI runs sync handlers in a threadpool automatically, so this isn't broken, just not the fully-async design originally sketched. Revisit (asyncpg + async route handlers) if request volume ever makes the threadpool a real bottleneck; not worth it for a single-user hobby project today.
- `MIN_RELIABLE_INCIDENTS`'s hard 100-incident floor (see "Database & query library") is a heuristic, not a validated test — could misclassify a genuinely low-crime rural county the same as a non-reporting one like NYC. A real fix would cross-check against known agency-participation data (e.g. the FBI's `ucr_participation` bulk file, listed as a manual crime-data option but not currently downloaded) rather than inferring non-reporting purely from a low incident count.
- No caching on the DeepSeek call — every request re-generates commentary from scratch (~4s latency, real API cost per call, even though cheap). Same location queried twice pays twice. A cache keyed by (lat/long rounded, endpoint, comparison params) would fix both; not built since it wasn't clear yet how much repeat-query traffic this will actually see.
- `api/main.py`'s blanket `except Exception` → 500 handler means a real bug (e.g. a DeepSeek timeout, a bad DB query) currently looks identical to any other internal error from the client's perspective — fine for now, but no logging/alerting exists to notice it happened at all.
- `/neighborhood?utterance=...`'s `"compare"` intent doesn't parse *which* home the utterance names — `"compare to LA"` silently compares against `home_zip`'s default (`10002`, NYC) unless the caller separately passes `home_zip` as its own query param. Resolving a named place in the utterance to a ZIP would need either a city/ZIP lookup table or a second LLM extraction step; not built, since the Siri Shortcut use case as scoped always compares to one fixed home ZIP anyway.
- `classify_intent` (in `api/llm.py`) is an extra DeepSeek round-trip on top of the commentary call whenever `utterance` is passed, and still runs even when `commentary=false` (category selection is needed either way, no way to skip it and pass categories directly). Measured live, not assumed: total latency with `utterance` set (~2.9s) was not meaningfully worse than without it (~3.1s) — the classification call is small (`max_tokens=100`, `temperature=0`) and its added time is within normal request-to-request variance. Worth re-checking if `classify_intent`'s prompt grows later.
